# 2026.242.1704 — feat(WP5): ship the wlroots tooling the wl: verb shells out to

## Summary

Ships the wlroots tooling the `wl:` verb shells out to, so the verbs `plugin-wl` already serves
actually work on this compositor.

`wl:` implements clipboard via `wl-clipboard` (wl-copy/wl-paste over `wlr-data-control`), type and
key-combo via `wtype`, and resolution via `wlr-randr`. **None of them were in this image** — only
`grim` was — so those verbs failed on a **missing binary** rather than on anything about the
desktop. That is why none of them had ever been exercised against this nested Hyprland.

```
- grim            (already here — screenshot)
+ wl-clipboard    (clipboard)
+ wtype           (type, key-combo)
+ wlr-randr       (resolution)
```

## Why not compose `layer-wl-tools`, which bundles exactly these

That was the first attempt, and the bed rejected it:

```
FAIL  the wlrctl wloots control tool is installed  [layer-wl-tools:2]  exists=false, want true
```

`wlrctl` is an **AUR** package, and the cstream boxes declare `build: [pac]` — so it never installs
and the layer's own check fails. Adding `aur` to the box for a package nothing here uses would be
the wrong fix. The layer also brings:

| package | why not here |
|---|---|
| `xdotool`, `xorg-xprop`, `xorg-xwininfo` | X11 tooling on a pure-Wayland desktop |
| `ydotool` | uinput — the evdev surface this stack deliberately does not take |
| `wlrctl` | AUR; forces the `aur` builder into a `pac`-only box |

Four unused packages and a builder, to obtain three. So the three go here, beside `grim`, which
already lives here for the same reason: **the compositor primitive owns the tools that drive it.**

## The check is per-BINARY, not per-package

```sh
for b in grim wl-copy wl-paste wtype wlr-randr; do
    command -v "$b" >/dev/null 2>&1 || { echo "WL-TOOL-MISSING: $b"; exit 1; }
done
```

The failure this prevents is a verb dying on `command not found` at runtime, and only the binary's
presence predicts that. A package check would also pass on a rename that moved the executable — and
it names *which* tool is missing, rather than failing the whole set anonymously.

## ⛔ A finding this surfaced: `wl: resolution` is unsafe on a cstream desktop

With `wlr-randr` present, `wl: resolution` became testable — and it should **not** be offered here.
Measured in one bed run:

```
WP4 resize 640 480       ->  streamer 640x480,  compositor followed to 640x480   (coherent)
wl: resolution 1280x720  ->  compositor 1280x720          ("Set WAYLAND-1 to 1280x720")
streamer `geometry`      ->  STILL 640x480                (never told)
```

The compositor renders 1280×720 while the encoder is configured for 640×480, **with no error
anywhere**. `wlr-randr` is a second writer to a property the cstream control socket owns.

The plan's converse test says anything shelling out to `wlr-randr` "belongs to `wl:`". That is right
about ownership and wrong about safety on a GWD-driven output: offering it hands users a way to
desync the encoder from the compositor silently. **Resize must go through the cstream control socket
(WP4) only.** This PR therefore ships the binary — `wl:` serves other compositors where it is
correct — but the cstream bed deliberately does **not** gate that verb, and says so inline.
