# 2026.243.0216 — feat(WP5): give hyprlock a config — without one it cannot start at all

## Summary

**`hyprlock` has been shipping broken.** It is in this candy's `package:` list and has been since
the candy landed, but no config was ever staged — and hyprlock does **not** fall back to defaults.
This stages the config that makes it work, and gates it.

**Two changed paths, both accounted for:**

| path | change |
|---|---|
| `etc/hyprlock.conf` (new) | the minimum config hyprlock needs to render at all |
| `charly.yml` | stage it to `/etc/xdg/hypr/hyprlock.conf`, add `hypr-lock-config`, bump the candy `version:` |

## The defect, measured

Run in the live pod bed (`charly config` → `start` → `cmd`, hyprlock v0.9.6):

```
Hyprlock version v0.9.6
CRIT: Config path error: Could not find config.
      Searched in order: XDG_CONFIG_HOME, HOME, XDG_CONFIG_DIRS, /etc/xdg
```

…and the process **exits immediately**. So the candy has been shipping a lock screen that cannot
lock: the package is present, the feature is not. Nothing caught it because nothing asserted more
than the package.

With a config supplied, the same binary on the same compositor starts and the compositor confirms
the lock:

```
DEBUG: | got iface: ext_session_lock_manager_v1 v1
DEBUG:  > Bound to ext_session_lock_manager_v1 v1
DEBUG: onLockLocked called
```

One variable — the file — so the config was the only thing missing.

## Why `/etc/xdg` and why minimal

**`/etc/xdg/hypr/hyprlock.conf`, not a user's `~/.config`:** every session must get it, including
the ones the broker creates for accounts that have no dotfiles yet. A user config still wins,
because `XDG_CONFIG_HOME` and `HOME` are searched *first* — this is the floor, not a theme.

**Minimal on purpose:** the two blocks hyprlock requires to render. Fonts, images and layout are
per-deployment choices that belong in a user config, where they override this one.

## Why the check asserts the config, not the binary

`hypr-lock-config` asserts the file exists **and** carries both required blocks. A check that only
asserted the `hyprlock` binary was installed would have passed throughout the entire period the
feature was broken — the binary was always there. That is the failure this gate is shaped against.

## How tested

`charly check run check-cstream-pod` with this branch overridden in, on the final committed tree
(`8292a0d`). pod-hyprland cannot be gated standalone — a nested compositor needs a parent Wayland
display, so the pod bed is its venue.

```
  PASS  hyprlock has a config, without which it exits instead of locking  [hypr-lock-config]   <- build-scope leg
  PASS  hyprlock has a config, without which it exits instead of locking  [hypr-lock-config]   <- live leg

81 steps: 77 passed, 0 failed, 4 skipped
charly check run check-cstream-pod: PASS (steps=13)
  summary.yml: errors: 0   warnings: 0   allowlisted: 6   ok: true
```

The check runs in **both** the image and live scopes, which is right for a staged file: the build
leg proves it was installed, the live leg proves it survived into the running container.

```
$ CHARLY_PLUGIN_ONLY=1 charly box validate ; echo "EXIT=$?"
EXIT=0
```

## What this does NOT claim

**That locking blocks input is not gated here.** It is the property that would make a lock gate
complete, and I attempted to measure it — but my own `ps | grep` probes kept matching the command
text of the shell running them, the same self-match class that makes `pkill -f` unsafe here. Rather
than ship a gate resting on an unreliable measurement, that claim waits for a clean one.

What *is* established, and all this PR claims: without the config hyprlock exits; with it, hyprlock
runs and the compositor reports `onLockLocked`.

WP5's `lifecycle.rs` half — dispatching hyprlock after `detach_lock_after` — is product code in
`charly-streamer` and remains open.
