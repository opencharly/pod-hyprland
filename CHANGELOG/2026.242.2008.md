# 2026.242.2008 — fix: the nested compositor is session-scoped, not a multi-user.target service

## Summary

On the **systemd venue** the nested compositor was enabled into `multi-user.target` and started at
deploy time, and the deploy aborted. This scopes it to a session instead. Two keys, no schema
change, no Go.

```diff
-              enable: true
+              enable: false
+              wanted_by:
+                - cstream-session.target
```

### The defect

`charly fleet add` **starts what it enables**, at the `ServiceCustom` step of the candy being
walked. That walk reaches `pod-hyprland` *before* `pod-cstream` installs the streamer — so the
compositor was started with no parent Wayland display in existence. Hyprland nests; it aborts
without a parent. Its `wait_for` timed out and took the whole deploy with it:

```
Created symlink '/etc/systemd/system/multi-user.target.wants/charly-hyprland-cstream-hyprland.service'
Job for charly-hyprland-cstream-hyprland.service failed because the control process exited with error code.
charly: error: … plugin-deploy-vm: walk step "ServiceCustom" (candy=hyprland): exit status 1
```

The **supervisord venue cannot show this**: there, priority ordering (`cstream-parent` 10 →
`cstream-hyprland` 12) starts both at container start, by which time the image is complete. One
`service:` list, two renderings — and only the systemd rendering has a deploy-time start to get
wrong. This is exactly the class of defect the two-venue split exists to find.

### Why these two keys, and not the ones this repo's issue #5 originally recommended

**`enable:` is systemd-only**, and the container rendering provably cannot see it. No service
template in charly references `.Enable` at all:

```
$ grep -c '\.Enable' charly/charly.yml     # the file carrying all three init service_templates
0
```

`enable:` is consumed by the deploy walk (`systemctl enable`), never by a template. supervisord's
start-at-boot is a *different* field — `auto_start:`, rendered from `.AutoStart`:

```gotemplate
{{- if .AutoStart}}
autostart={{if derefBool .AutoStart}}true{{else}}false{{end}}
{{- else}}
autostart=true
```

This service sets no `auto_start:`, so its `[program:]` entry keeps `autostart=true` before and
after this change. The container rendering is therefore **byte-identical by construction**, not
merely observed to still pass — and `check-cstream-pod` passing with identical step counts (below)
is the confirmation, not the argument.

**`wanted_by:` is the first-class `[Install]` field.** `unit_options:` **cannot** express this:
charly's systemd template renders it inside `[Service]`, where a `WantedBy` is silently inert and
the `multi-user.target` default still wins. Measured — an identical failure, with the symlink
still landing in `multi-user.target.wants`. Issue #5's original option 1 recommended
`unit_options.systemd`; that recommendation was **wrong** and is corrected there.

Issue #5 also claimed `enable: false` was *rejected* by the schema (`conflicting values true and
false`) and concluded a per-venue `enable` was needed. **That was my own error**: the candy
already authored `enable: true`, I added a second `enable:` key rather than changing the existing
one, and CUE correctly reported my duplicate conflicting with the original. Nothing unifies the
field. Editing it in place is accepted — `charly box validate` exits 0. No schema change is
needed, and that option is withdrawn.

The `update` + `check-live-rebuild` legs are the R10 half: the guest is destroyed and rebuilt from
the pacstrap bootstrap and the five checks re-run against the new machine, so nothing above depends
on state left by an earlier run.

**`deploy-add` is the step that used to fail.** It now exits 0. The two counts that were the
symptom are gone: `Job for charly-hyprland…failed` — **0**; `added as a dependency to a
non-existent unit` — **0**.

`cstream-vm-compositor-session-scoped` is the assertion that discriminates. It fails if the fix is
absent *or* half-applied, because it checks three things and not one:

1. `/etc/systemd/system/charly-hyprland-cstream-hyprland.service` **exists** — so `enable: false`
   still *installs* the unit; it only stops the enable-and-start. This was the open question the
   fix rested on, and it is now measured rather than assumed.
2. `/etc/systemd/system/multi-user.target.wants/charly-hyprland-cstream-hyprland.service` is
   **absent** — the enable did not happen, and did not silently fall back to the default target.
3. the unit's `[Install]` carries `WantedBy=cstream-session.target` — proving `wanted_by:` reached
   the `[Install]` block, which is precisely what the rejected `unit_options.systemd` route could
   not do.

## Rulebook compliance

- **R0 — skills honoured.** `/charly-internals:git-workflow` for the branch/PR/landing mechanics;
  `/charly-internals:root-cause-analyzer` for the deploy failure, which is why the fix is two
  declarative keys rather than a reordering or a retry.
- **R1 — RCA every anomaly.** The deploy failure was traced to `ServiceCustom` starting what it
  enables, with the walk order as the aggravating condition — not patched at the symptom. Two
  earlier hypotheses of my own were measured and **refuted**, and both are corrected in
  `pod-hyprland#5` rather than left standing: `unit_options.systemd` cannot express `[Install]`,
  and the `enable: false` "schema rejection" was a duplicate key I had introduced myself.
- **R2 — nothing parked.** The issue is fixed here, not deferred; the issue's own wrong analysis is
  corrected in the same pass.
- **R3 — no duplication.** `wanted_by:` is the existing first-class field; nothing new is invented,
  and the discarded alternative would have duplicated `[Install]` semantics into `[Service]`.
- **R4 — no workaround.** No sleeps, no retries, no composition-order hack. The compositor is not
  "made to survive" a deploy-time start; it is declared not to have one.
- **R5 — delete legacy completely.** `enable: true` is replaced, not shadowed.
- **R6 — git safety.** `git status` before staging and clean after commit; `fix/` branch off a
  fresh clone of `main`; no force-push; no direct push to `main`; no hook bypass.
- **R7 — prove the gate, not the plan.** Both venues run live on the final committed tree, output
  pasted above — the systemd venue for the fix, the container venue for the no-regression claim.
- **R10 — fresh disposable proof.** Both beds are `disposable: true` and were destroyed and rebuilt
  from scratch; `check-cstream-vm` builds its guest image from a pacstrap bootstrap each run.

## Change classification

- **Change class:** candy manifest — one `service:` entry, two keys, plus the candy `version:`.
  No Go, no schema, no workflow, single repo.
- **Verification gate:** `charly box validate` + `check-cstream-vm` (the venue that has the defect)
  + `check-cstream-pod` (the venue that must not change).
